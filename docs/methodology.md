# 用 AI 定时任务运营多平台矩阵：一套能自我进化的规则系统

这份文档记的是工作台背后的运营做法：每天由十几个 AI 定时任务（早班、午班、晚班、热点雷达、账号互动、数据回流、日报、周进化）按同一套手册运营 8–10 个账号。工作台是观察层，规则系统才是让它跑起来的部分。

## 1. 目录约定

```
运营手册/00-必读.md      唯一入口：版本号、规则优先级、硬规则、各任务职责、改规则流程
运营手册/运营计划.md      数据驱动的当前计划：生效中的调整、实验、需要拍板、待修问题
运营手册/<专题>.md        具体做法：内容总纲、批次执行、平台打法/<平台>.md、互动、热点、数据回流……
运营手册/变更日志.md      每次升版写一条：时间、来源（用户/数据/事故/运营）、改了什么、涉及文件
config/schedule.json     账号、发布时段、配额（机器可读的唯一来源）
config/experiments.json  A/B 实验
config/playbook_rules.json  作废说法的正则，供体检使用
state/                   台账、作品数据、粉丝（sqlite / json）
days/<日期>/             每条内容一个目录：post.json、成品、review.md；运行记录、雷达、互动流水
reports/<日期>.md        日报
```

## 2. 规则只有一个入口

**问题**：一开始每个定时任务的提示词里各抄了一份规则。手册改了，提示词没改，体检时查出 52 处冲突，定时任务一直按旧规则在跑。

**做法**：
1. **单一入口**：所有任务开工第一件事读 `00-必读.md`。提示词只写「你是哪个任务」和开工三步，不写任何具体规则。
2. **优先级**：冲突时从上往下取，依次是：用户亲口定的硬规则（锁定，自我进化不能改）> 运营计划里数据驱动的调整 > 专题手册 > 提示词。同一级冲突以日期新的为准。
3. **发现冲突不要私下绕过去**：这一次按优先级高的做，同时在「待修问题」记一行，由日报统一修。
4. **改规则四步，必须在同一轮做完**：改专题手册 → 把旧说法加进作废正则 → 体检到 0 错误 → 升版本、写变更日志。只写进对话记忆的不算数，定时任务读不到记忆。
5. **开工脚本**（`playbook.py start <任务>`）打印这几样：手册版本、体检结果、生效中的调整、今天的实验分组。同时在 `runs.jsonl` 记一条开工，工作台据此显示任务有没有在跑。

## 3. 发布台账：所有发布都要先入账

- 一条内容一个台账条目，状态依次是：draft → checked → ready → submitting → submitted / scheduled → success / public。失败记 failed 或 blocked，结果不明记 uncertain。
- **入账前跑内容体检**：营销词、AI 腔、篇幅、话题数、标题字数、栏目有没有写。有错误就拒收。
- **防重复**：状态是 uncertain 的条目禁止直接重发，先去平台核实；换发布通道前先把原条目冻结；网页发布要先占位、再发布。
- **按内容算，不按尝试次数算**：同一天同账号同标题的多次尝试只算一条内容。成功率 = 发出 ÷（发出 + 最终失败）。「一次成功率」另外统计，它反映的是发布通道稳不稳。
- **失败要归类**：登录失效、网络/代理、账号配置、审核/风控、素材/参数、超时。每一类对应一种处理方式，别一律重试。

## 4. 自我进化：每天小改，每周大改

```
发布（带栏目、实验分组标签）→ 数据回流（每天两次采创作者中心）→ 每日进化（日报）→ 每周进化 → 改计划和手册、升版本 → 第二天按新版本跑
```

- **每日进化**：只根据有样本量的结论调整，每天最多 3 条，写进「生效中的调整」，每条带依据（数字和样本量）和复查日。样本不够的想法只能写成实验或「观察」。
- **每周进化**：重排平台优先级和时段配比，开停实验。降配额、停平台、超预算、改用户定稿的东西，都必须交给用户拍板。

### 判断口径：别被小样本带偏

- 发布不满 24 小时的作品不参与任何结论。
- 比率类指标（评论率、互动率）只算播放达到一定量的作品；留存类指标（2 秒跳出、5 秒完播）只算播放 ≥200 的作品。
- 跨平台比较用「相对本平台中位数的倍数」，不比绝对值。
- 同一内容在两个平台差 10 倍以上，是分发问题，不是内容问题：调平台配比，而不是改内容。
- 一条调整至少要有 3 条可比作品指向同一方向。

### 实验设计：先算样本，再开跑

我们犯过的错：开了一个看「2 秒跳出率」的实验，可那个号单条只有个位数播放，而口径规定留存指标只算播放 ≥200 的作品，所以永远判不出来；另一个看评论率，全库一共才 2 条评论。

- **开跑前估算每组要多少条**。比率指标可以用两比例检验粗算：要分清 0.5% 和 1% 的评论率，每组大约需要 4700 次播放。播放倍数这类偏态指标先取对数：σ≈0.7 时，测出 2 倍差距每组约 16–20 条，测出 1.5 倍要 45–50 条。
- **同一时间只跑一个实验**，放在有量的平台上，每次只改一个大杠杆变量（系列 vs 单条、时长、发布时段），不测细枝末节。
- **用置信区间判定**，别用「两组差 ≥15% 就算有差别」这种固定阈值。

## 5. 我们踩过的坑

1. **规则膨胀**：手册涨到 25 万字，硬规则 43 条，一大半是脚本已经保证的参数。执行者读不完，也记不住。参数检查应该交给脚本，必读里只留行为红线。
2. **改得太勤**：一天升版 15 次，早班跑一趟就跨了 5 个版本，中途改规则导致整条内容返工。用户提的新要求照常立刻同步；执行中发现的问题先记下来，攒到日报统一修。
3. **体检只查旧说法，查不出语义冲突**：同一个参数在两份手册里取值不同，正则抓不到。后来人工查出 9 处。
4. **发布通道单点**：所有账号挂同一个代理，代理一坏，四个平台一起失败；判断恢复又要等真实内容去试。应该用探测请求，并且准备好平台级的网页兜底。
5. **作品数据和台账对不上**：平台抓回来的标题和我们写的标题不一样（视频号抓到的是描述文字），导致栏目全都显示「未标」。匹配要有多级兜底：作品 id → 标题加日期 → 同账号发布时间 40 分钟内。
6. **投入产出倒挂**：最费工的平台没量，有推荐的平台只是搬运。工作台的「投入产出」表就是为了尽早发现这种情况。

## 6. 工作台和规则系统怎么配合

| 规则系统里的东西 | 工作台在哪看 |
|---|---|
| 手册版本、当天升版次数 | 右上角数据源健康、运营计划 → 版本时间线 |
| 定时任务有没有在跑 | 总览「今日任务运行」，运营计划 → 任务运行 |
| 台账、失败原因、处理建议 | 总览「待处理」，日历 → 失败原因 |
| 每日/每周进化的建议 | 运营计划 → 数据进化 |
| 实验进度（样本数 / 需要的样本） | 运营计划 → 实验看板 |
| 投入产出、目标进度 | 增长 |
